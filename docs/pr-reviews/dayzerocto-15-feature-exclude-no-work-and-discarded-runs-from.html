Summary

The weekly streak is this product’s North Star, but it counted every dated weekly report on disk — so a quiet week with zero commits, or the maintainer’s own test render, extended it exactly like a genuine week of shipped work. This group makes the streak trustworthy (exclude no-work and test/debug runs), visible (print it after every run), defensible (warn before it resets), and turns the shared report into a discovery surface for the project.

What changed

  • A weekly report rendered against a zero-commit evidence snapshot for its own window no longer extends the streak.
  • dzcto artifact --test-run marks a render as a test run so it never counts.
  • Every report run now prints the current streak to stderr, and warns when the streak is one period from resetting.
  • The index streak tile gains two states: Paused — report logged, not counted and At risk — report now to preserve streak.
  • Every generated page footer carries a linked “Generated with Day Zero CTO” credit.

Design / flow change

The shape of the change: one predicate (counts_toward_weekly_streak) applied at one dispatch point (classify_weekly_reports), feeding three consumers — the streak count, the stderr exclusion notes, and the index tile.

Why this approach

The repo’s own learnings decided it. Helper computes, agent narrates means streak eligibility is checkable, so the renderer computes it and the agent is forbidden from authoring it — both fields are stripped from authored input and stamped by the renderer, following the prior_report precedent. One predicate, N consumers, one dispatch point means the CLI line, the stderr notes, and the index tile cannot disagree, because they all read one function.

Facts, not verdicts. The stamped object stores observations (quiet, commits, merges), never a baked counts_toward_streak boolean — so a future policy change does not require rewriting historical artifacts.

Other options considered
  • Agent authors quiet: true — rejected: the party the metric measures would be scoring its own homework.
  • Infer quiet from empty report sections — rejected: an in-source comment already documents that this cannot distinguish an intentional quiet window from forgotten structure, and carried-forward risks suppress it.
  • Recompute quietness at streak time — rejected: non-deterministic over time (a rebase changes the answer for a closed window) and impossible once the evidence repo is gone.
  • Locate the snapshot by filename convention instead of a flag — rejected: --output-json can redirect it, and a silently missing file at a guessed path is indistinguishable from “no evidence collected.”
Tradeoff

The product tells the agent to prefer an honest quiet-week report; this change makes that same report stop extending the streak. The resolution is that the exclusion must be legible, not punitive: named stderr reasons, and an index tile that reads Paused rather than Start a weekly report, in the info tone rather than the warn tone.

Backward compatibility is the load-bearing decision. An absent eligibility fact means the report counts — the opposite of report_type, where absence excludes. Excluding on absence would retroactively zero every existing user’s streak on upgrade, converting a known over-count into total loss of the signal.

Questions / gaps
  • Only two of the four PRODUCT_STRATEGY North Star exclusions are implemented. “Automated runs nobody opens” needs open/read telemetry the product does not collect; “the maintainer’s own usage” needs an identity concept it does not have. Both are explicitly out of scope.
  • The Independent Test Gate could not run in this environment (no subagent tool), so the 12 acceptance criteria have no independently-derived coverage. The branch’s own 280 tests cover them, but without an information barrier.
  • Exact stamped key names were deferred to implementation and settled as test_run / work_evidence; they are pinned by a docs test so a rename cannot skip the docs.
  • The CLI streak tail swallows all exceptions (except Exception: pass) — deliberate warn-never-fail on an already-successful write path, but it would hide a genuine bug in the message construction.
