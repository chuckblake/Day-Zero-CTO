What changed

  • The index's Defaults section now lists profile name, defaultProfile, evidence repos (basenames + count), and tool version alongside the existing weekly range and tone.
  • That section is now collapsed by default, so a CEO-facing share is not led with operator settings.
  • A new settings.html is generated beside index.html on every dzcto init / dzcto artifact run, listing each report-shaping flag, its config key, the reader's current value, and what it sets.
  • That page states the two non-obvious semantics: dzcto init merges over the existing profile, and saving switches defaultProfile unless --no-switch-default is passed.
  • A parity test pins the documented flag table against the real dzcto init argparse surface, so a renamed or invented flag fails the suite.

Details

Why this approach — a generated page, not a repo doc

The acceptance criteria require the documentation be viewable in the browser from the index. A shared artifact tree travels without a repo checkout, so a docs/*.md link would be dead for exactly the reader this feature targets. The cost is a second write_html_page + update_manifest pair — one function following an existing precedent.

Content drift is prevented structurally rather than by discipline: a single module-level INIT_REPORT_SETTING_FLAGS table is the source of truth, and a parity test pins it against the real CLI. skills/dzcto-init/SKILL.md got a pointer, not a copy.

Other options considered
  • Linked repo doc — cheapest, but not viewable from a shared artifact tree.
  • Static settings.html copied at init — cannot show the reader their current values, and reintroduces the drift problem.
  • Refactor build_parser() out of main() so the parity test could introspect argparse — rejected as scope creep; source-text matching catches the same regression with a far smaller blast radius.
  • Add the values as KPI tiles — rejected: clutters the CEO-facing top of the page, and both existing KPI test helpers slice the page by tile label.
Tradeoff — a new coupling and a test-hermeticity hazard

defaultProfile lives in the global ~/.dzcto/config.json, not the workspace sidecar project_config() reads. Rendering it means render_index now transitively calls read_global_config(), whose path is a module-level constant with no env seam. Before this branch, no index test touched the developer's home directory.

Mitigation: profile_config_view() takes an injectable global_config, and the two pre-existing index suites now pin read_global_config in setUp. They passed either way — but only because no assertion happened to read a global-derived value, which is luck rather than design. The smoke test confirmed the hazard is real: it rendered Global defaultProfile: arwen from the live machine config.

Questions and gaps
  • Known, out of scope: index.html still emits absolute repo paths twice, via the pre-existing copyable prompt cards and the "Serve Index" command card. This predates the branch and the acceptance criteria explicitly permit it ("config paths are fine"). The new panel and settings page are deliberately stricter. Tightening the older surface is its own issue.
  • Cosmetic: the three weekly day/lookback rows on the settings page all repeat the same combined weeklyRangeLabel.
  • Cosmetic: a fresh workspace renders not_configured; Not set to Not set.
  • Deliberate asymmetry: tone reads "Not set" on the settings page (answering "what have you configured?") while the index shows the effective default (answering "what voice do reports use?"). Recorded in the plan's decision log.
  • Deferred: no build_parser() refactor; revisit only if something else needs the parser independently.
