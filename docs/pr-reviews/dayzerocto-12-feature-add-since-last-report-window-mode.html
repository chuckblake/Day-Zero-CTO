Summary

Weekly CEO report windows were resolved by an agent reading weeklyReportDefaults prose, so a day-based rule like previous_completed_week produced a different window depending on which day the report was run — two honest runs could overlap or leave a gap. This adds a deterministic dzcto window CLI resolver and a since_last_report range that anchors each window on the previous weekly report's window.end, so every calendar day lands in exactly one report. Reviewers should focus on the cursor-selection rule and the empty-window contract.

What changed

  • New hidden dzcto window subcommand emits one JSON object describing the run's window (mode, start, end, days, empty, cursor, fallback_reason). All diagnostics go to STDERR so STDOUT stays machine-parseable.
  • weeklyReportDefaults.range accepts since_last_report; the window becomes (previous weekly report's window.end + 1 day) … run date.
  • Skipping a week self-heals — the next report simply covers the whole elapsed span. No cap.
  • The report index KPI no longer describes a cursor-mode profile as "Fri to Thu"; it reads "Since last" and suppresses stale weekday keys.
  • The week-over-week section now states each window's length beside the metric deltas, so a 9-day window is never silently compared against a 7-day one.
  • skills/dzcto-ceo-report-weekly now consumes the resolver instead of interpreting the config, including an explicit branch for the already-covered case.

Manual check — resolve a window against a throwaway artifact folder:

tmp=$(mktemp -d); mkdir -p "$tmp/.dzcto" "$tmp/reports/ceo-updates"
echo '{"weeklyReportDefaults":{"range":"since_last_report"}}' > "$tmp/.dzcto/config.json"
echo '{"report_type":"weekly","window":{"start":"2026-07-08","end":"2026-07-14"}}' \
  > "$tmp/reports/ceo-updates/2026-07-14-ceo-report.json"
python3 scripts/dzcto.py window --artifacts-dir "$tmp" --as-of 2026-07-23
# expect: mode since_last_report, start 2026-07-15, end 2026-07-23, days 9

Rollback plan — no migration and no persisted state; the cursor is derived on every call. Reverting the branch restores the previous behavior, and any profile still on a day-based range is unaffected either way.

Details

Why this approach

The report JSON already stores window.end, so a cursor needs zero new state — the next window derives directly from the newest weekly report. Anchoring on PRs instead would require recording per-report PR coverage, and PRs are not the only evidence (direct commits, notes, and CI events all feed a report).

Ending at the run date rather than the last merged PR deliberately keeps quiet tails in the record: a quiet stretch is signal, not noise, and gapless coverage protects the streak metric that a double-counted or missed window would corrupt.

Other options considered
  • A --range flag on dzcto evidence instead of a new subcommand — rejected: the window is needed even when zero repos are configured, and it feeds three consumers (the evidence call, the report's window field, and the report title). Folding it in would let the collector's "no configured repos" degradation also lose the window.
  • Cursor = newest report of any type — rejected: an ad-hoc report would silently swallow days out of the weekly ritual, which is the exact gap this change closes.
  • Porting all day-based modes into the resolver — deferred: it would triple the diff. The resolver instead returns an explicit day_based deferral so the skill's fallback is a declared branch rather than an accident.
Tradeoffs
  • Deliberate asymmetry with locate_prior_report. The coverage cursor is weekly-scoped; the week-over-week diff baseline still falls back to any report type. Same file, different rules, because one is a coverage ledger and the other is a narrative comparison baseline.
  • Varying window lengths make deltas less apples-to-apples. Accepted per the issue — surfaced via the window-length line rather than normalized away.
  • range stays unvalidated free text. An allow-list would reject untyped values operators already have on disk and turn a config typo into a hard init failure.
  • snapshot_window is deliberately not reused. It SystemExits when start > end, which is a legitimate state here.
Questions and gaps
  • Deferred: previous_completed_week / last_7_days / lookbackDays are still resolved by the skill, not the CLI. Worth a follow-up once cursor mode has real usage.
  • Not covered by tests: the added help-text lines in print_quickstart and command_reference_text. Purely additive prose; no consumer assumption depends on them.
  • Ordering hazard worth knowing: a report written with a wrong window.end poisons the next window too. The fix is to correct the report JSON, not just re-run.
  • Scope gate did not evaluate this branch — the plan declares files per-unit rather than in a top-level ## Files section, which scope-check reads as an empty allowlist and fails open.
