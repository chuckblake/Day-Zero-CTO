Why this approach

The goal is not merely to create an example report; it is to ensure that one new artifact can coexist with six existing readers of reports/ceo-updates/ without becoming fabricated evidence.

The plan centralizes that contract in is_sample_report(). An additive sample: true marker is smaller and stricter than introducing another report type, because the sample can remain a realistic weekly report while every evidence-bearing consumer applies the same exclusion rule.

Artifact creation stays in the deterministic helper, and the init skill reports the result. Date-dependent sample data uses an injectable today value so tests can remain hermetic.

Other options considered
  • New report_type: "sample" — rejected. It would expand report-type validation and schema surfaces while failing to protect prior-report selection, which coerces unknown types to ad_hoc.
  • Plausible sample sources — rejected. The sample uses sources: [] so the existing thin-evidence banner remains truthful and no citations are fabricated.
  • Delete the sample after real reports exist — rejected. The selected behavior avoids deleting user files; creation is suppressed when real reports exist, while an existing sample remains excluded and badged.
  • Store the opt-out as workspace configuration — rejected. --no-sample-report is treated as an operator-only flag with no stored configuration key.
  • Fix the pre-existing company-name page-chrome egress gap — rejected for this branch. The plan records it as a separate shared-chrome concern outside this feature’s scope.
Tradeoffs
  • Keeping the sample permanently avoids destructive cleanup, but every future reader of the CEO-report glob must consciously route evidence selection through the shared predicate.
  • Treating missing or corrupt sample metadata as real is the documented fail-safe direction for the index; this avoids crashes but can temporarily lose the exclusion when the sibling JSON is unavailable.
  • The sample is intentionally included in format refresh while excluded from evidence selection. That two-direction rule preserves current rendering without contaminating counts or comparisons.
  • Adding first-run output required retargeting absence-based tests so they continue to assert whether a blocked operation authored a report, rather than whether the folder is completely empty.
Design / flow change

The diff represents a structural call-path change: initialization can now build and write a sample artifact, while a shared predicate is consumed in opposite directions by evidence-selection and format-refresh paths.

dzcto init refreshes existing report pages.
If no real report exists, no sample already exists, and opt-out is absent, it builds sanitized sample data.
The writer creates sample-ceo-report.html and its sibling JSON, updates provenance and manifest state, and never writes the rolling data.json pointer.
The shared renderer places the sample banner above the thin-evidence banner.
The index exposes the sample card, while report counts, latest selection, streaks, status, prior-report lookup, and reporting-window cursors exclude it.
